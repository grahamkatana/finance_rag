## Answer check returned 500 — fixed
- **Cause:** `JUDGE_MODEL=deepseek-v4-pro:0813` is not on the Ollama free tier (HTTP 402 from Ollama).
  Of the 17 Ollama cloud models, 6 are: `gemma4:31b`, `gpt-oss:120b`, `gpt-oss:20b`, `nemotron-3-nano:30b`,
  `nemotron-3-super`, `nemotron-3-ultra`. All six scored a grounded / partial / hallucinated answer
  1.0 / 0.5 / 0.0 with the app's own prompts.
- **Fix:** judge switched to `gpt-oss:120b` (different family from the answer model, ~1 s per call).
- `app/features/generation/eval_router.py` — a judge failure is now a 503 with a readable message;
  the provider's own error is logged. Test added. `uv run pytest` — 234 passed.
- Deployed as API `v0.1.8`; one live check returned scores in ~6 s.

## Evening — 500s, lost history, repeated sources, routing
- **500s on ask / check answer:** Voyage's free tier allows 3 embedding requests a minute, and one question spent
  three (answer, source list, answer check). `app/features/retrieval/service.py` now caches the query vector
  (`embed_query`, 15 min, in-process), so a question costs one. Embedding failures raise
  `EmbeddingUnavailableError`, mapped in `app/main.py` to a 503 with a readable message and `Retry-After`.
  `/generation/generate` retrieves before it starts streaming, so that failure is an HTTP error, not a cut-off answer.
- **History not saved:** no Celery worker was deployed, so audit tasks were only ever queued. Added a `worker`
  container to `05-app.yaml`. First run exposed a latent bug: `app/database/audit.py` pooled asyncpg connections
  across tasks that each call `asyncio.run()` ("another operation is in progress"). Now `NullPool`; reproduced
  before/after on a real Postgres.
- **Frontend:** sources grouped by document with numbered passages; pages have URLs (`/`, `/documents`,
  `/activity`, `/users`); the conversation is kept in the browser across reloads (cleared on log out), with a
  "New chat" button; the source list is requested after the answer starts so it reuses the cached embedding.
- Tests: 239 passed. Deployed: API `v0.1.10` (API + worker), frontend `v0.2.1`.
- Still open: Voyage is limited to 3 requests/min until a payment method is added, so three *different* questions
  inside a minute (or an upload plus questions) can still be refused, now with a readable message.

## Embeddings moved from Voyage to OpenAI
- **Why:** Voyage's free tier caps the account at 3 embedding requests a minute.
- **Now:** `EMBED_PROVIDER=openai`, `EMBED_MODEL=text-embedding-3-small`, `EMBEDDING_SIZE=1536`,
  `QDRANT_COLLECTION=finance_docs_openai`. The old `finance_docs` collection (Voyage, 1024 dims) is untouched.
- `app/core/qdrant.py` — new collections are created with int8 scalar quantization, `always_ram=True`
  (same reason as books_rag: the shared Qdrant pod is memory-capped; see `books_rag/QDRANT_QUANTIZATION.md`).
- `app/reembed.py` — `uv run python -m app.reembed` re-embeds every chunk from Postgres into the configured
  collection, keeping point ids and payloads, so nothing is re-uploaded and ownership/sharing are unchanged.
  Run on the cluster via `finance-rag-k8s/08-reembed-job.yaml` BEFORE switching the Deployment's settings.
- Tests: `tests/test_reembed.py`, `tests/core/test_qdrant.py`; suite 243 passed. Also run end to end against a
  throwaway Postgres + Qdrant (150 chunks, re-run is idempotent).
- Deployed as API `v0.1.11`. Live check: 6 different searches in a row succeeded (twice the old cap), an answer
  and an answer check both worked. The collection held 3 chunks (one document, `finance_test.pdf`).
